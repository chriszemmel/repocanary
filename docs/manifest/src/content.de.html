01

Was wir glauben

Wer ein fremdes Repository ausführen soll, hat meist ein paar Minuten und kein Werkzeug dafür. RepoCanary gibt dieser Person eine schnelle, kostenlose und ehrliche Einschätzung. Das Projekt folgt sieben Grundsätzen. Jeder ist im Code umgesetzt, und hinter jedem steht ein echter Fall.

1

Lesen, nie ausführen

RepoCanary klont, installiert, startet, wertet und importiert das geprüfte Repository nie. Es liest Dateien als Text und vergleicht Muster.

Warum

Ein Werkzeug, das fremden Code zum Prüfen ausführt, wäre selbst der Angriff. Wer RepoCanary auf Schadcode richtet, darf dabei nicht mehr riskieren als beim Lesen im Browser.

Der Fall

Ein Test bricht den Build, sobald der Code der Engine child_process importiert, eval nutzt oder einen anderen Host anspricht als die GitHub-API und, nur auf Wunsch, einen KI-Anbieter (test/invariants.test.js). Als die Dokumentation „nie heruntergeladen“ versprach, wurde sie korrigiert: Dateien werden zum Prüfen in den Speicher gelesen, aber nie ausgeführt oder gespeichert.

2

Grün heißt nicht sicher

Ein grünes Urteil sagt „nichts Bekanntes gefunden“ und nie mehr. Ein Scan, der nicht fertig wurde, gibt sich nie als einer aus, der nichts gefunden hat.

Warum

Falsche Entwarnung ist das teuerste Ergebnis, das ein solches Werkzeug liefern kann. Wer „sicher“ liest, führt aus. Eine Prüfung, die nicht hinsehen konnte, darf nicht so aussehen wie eine, die nichts fand.

Der Fall

Der Satz für Grün steht an einer Stelle im Code und wird überall wörtlich verwendet. Ein Test prüft, dass er ausdrücklich sagt: kein Beweis für Sicherheit. Ein unvollständiger Scan endet mit Exit-Code 3, schreibt trotzdem ein JSON- oder SARIF-Dokument mit dem Urteil „error“ und lässt die GitHub Action bei jeder Einstellung scheitern.

3

Rot muss man glauben können

Rot bleibt dem Muster einer Falle vorbehalten. Was unsicher ist, wird Gelb. Wie oft Rot ein ehrliches Projekt trifft, wird auf fremdem Code gemessen, nicht geschätzt.

Warum

Eine Warnung, die auf ehrliche Projekte feuert, bringt Menschen bei, sie zu überspringen. Dann ist auch das echte Rot wertlos.

Der Fall

In der ersten Messwelle waren rund 13 Prozent der roten Urteile falsch. Jeder Fehler wurde mit einem allgemeinen Grundsatz behoben, nie mit einer Ausnahme: Rot braucht etwas, das von selbst läuft. Ein Text ist kein Befehl, solange er keine Shell erreicht. Eine Erwähnung ist keine Handlung (Kapitel 9).

4

Die Grenzen stehen im Repository

Was RepoCanary nicht erkennt, steht im Bedrohungsmodell. Die wichtigsten Grenzen liegen als Beispiele bei, die weiter unerkannt bleiben müssen.

Warum

Ein Sicherheitswerkzeug, das seine Grenzen verschweigt, täuscht gerade die Menschen, die die Wahrheit am dringendsten brauchen.

Der Fall

Sechs dokumentierte Grenzen liegen als ausführbare Beispiele bei, und die Messung prüft, dass sie weiter durchrutschen: Eine Grenze, die sich still verschiebt, fällt auf. RepoCanary meldet sein eigenes Repository als Rot, weil es seine Signaturen enthalten muss. Eine Ausnahme dafür wäre ein Weg zum Umgehen, also gibt es keine.

5

Ein Modell entscheidet nie über Rot

Eine KI-Zweitmeinung ist möglich, aber nur auf Wunsch und mit dem eigenen Schlüssel. Sie darf ein Gelb freigeben oder ein Grün anheben. Ein Rot senken oder erzeugen darf sie nie.

Warum

Rot heißt: Eine Signatur hat gefeuert. Die Meinung eines Modells ist keine Signatur. Und Modelle lehnen Fragen zu Schadcode oft ab, das Urteil darf daran nicht hängen.

Der Fall

Die Grenze steht im Code, der das Urteil zusammenführt, nicht im Prompt, und Tests halten sie fest. Lehnt ein Anbieter ab oder fällt aus, kommt der nächste dran, danach gilt das statische Urteil. Als die KI die Länge der gekürzten Befundliste statt der wahren Zahl erhielt, wurde das korrigiert.

6

Feindliche Eingaben sind der Normalfall

Was RepoCanary liest, hat oft ein Angreifer geschrieben. Jede Regel muss präparierte Dateien aushalten, ohne zu hängen, abzustürzen oder die Ausgabe fälschen zu lassen.

Warum

Ein Scanner, den eine einzige präparierte Datei lahmlegt oder zu einem leeren Bericht bringt, liefert genau dann nichts, wenn es darauf ankommt.

Der Fall

Jede Regel ist auf linearen Aufwand festgelegt, gemessen an feindlich gebauten Dateien in der größten zugelassenen Größe. Scheitert eine Regel dennoch, kostet das nur die Befunde dieser Datei. Steuer- und Richtungszeichen werden vor der Ausgabe entschärft, damit kein Repository das Terminal täuschen kann.

7

Offen und kostenlos

Code und Regeln sind unter MIT-Lizenz öffentlich. Es gibt kein Konto, keine Telemetrie und keine Bezahlstufe.

Warum

Die Person, für die RepoCanary gedacht ist, kann sich keinen Scanner kaufen. Und einem Sicherheitswerkzeug, das niemand prüfen kann, sollte niemand vertrauen.

Der Fall

Die Kommandozeile hat keine Laufzeit-Abhängigkeiten, ein Lint-Schritt erzwingt das. Das npm-Paket wird über Trusted Publishing mit Herkunftsnachweis veröffentlicht. Ein Token zum Veröffentlichen gibt es nirgends.

{{I:triangle-alert}} Rot

Eine Signatur hoher Schwere passt. Nicht ausführen, nicht installieren, nicht in einem Editor öffnen, der Aufgaben selbst startet.

{{I:eye}} Gelb

Etwas sieht verdächtig aus, hat aber in manchen Projekten eine ehrliche Erklärung. Erst jemanden die genannten Zeilen lesen lassen.

{{I:circle-check}} Grün

Nichts Bekanntes passt. Das senkt das Risiko, beweist aber keine Sicherheit, und der Bericht sagt das.

02

Das Problem

Jemand schickt ein Repository und bittet darum, es auszuführen oder nur zu öffnen: ein Recruiter mit einer Probeaufgabe, ein „Kunde“, jemand, der eine zweite Meinung möchte. Der Schadcode sitzt dort, wo er läuft, bevor man etwas gelesen hat.

{{FIG:attack|Abb. 1|Der Angriff. Ein Repository kommt mit der Bitte, es auszuführen. Ob über die Installation, das Öffnen des Ordners oder den ersten Start: Der Schadcode läuft, bevor jemand den Code gelesen hat, und stiehlt, was auf dem Rechner liegt.}}

Kampagnen wie „Contagious Interview“, die staatlichen Akteuren aus Nordkorea zugeschrieben werden, haben das gegen Tausende Entwickler eingesetzt. Ihre Werkzeuge werden inzwischen von gewöhnlichen Kriminellen kopiert. Ein postinstall-Skript, eine verschleierte Konfigurationsdatei, ein manipulierter Eintrag in der Lockfile, oder ganz ohne Installation: ein VS-Code-Task, der beim Öffnen des Ordners startet, ein MCP-Server, den ein KI-Editor von selbst startet, ein Agent-Hook oder ein Dev-Container.

{{I:hourglass}} Läuft vor dem Lesen

Die Falle sitzt in Install-Hooks und Autostarts. Wer erst lesen will, muss wissen, wo.

{{I:folder-open}} Öffnen reicht

Für manche Wege braucht es keinen Befehl. Den Ordner im Editor zu öffnen, um ihn anzusehen, ist schon der Angriff.

{{I:file-search}} Code als Köder

Der sichtbare Code ist oft harmlos. Er lädt nur nach, was erst zur Laufzeit kommt.

03

Die Idee

RepoCanary prüft, bevor der Code den Editor oder das Terminal erreicht, und es liest nur. Wer es auf Schadcode richtet, setzt sich keinem größeren Risiko aus als beim Lesen der Dateien im Browser.

{{FIG:safe|Abb. 2|Lesen, nie ausführen. RepoCanary holt den Dateibaum und ausgewählte Dateien als reinen Text über die GitHub-API. Nur auf Wunsch gehen Befunde an einen KI-Anbieter. Klonen, installieren, ausführen, auswerten und importieren gibt es im Code nicht, und ein Test bricht den Build, wenn sich das ändert.}}

Aus dem Repository liest RepoCanary eine begrenzte Auswahl an Dateien. Jede Prüfung ist reiner Text- und Mustervergleich. Der geprüfte Link geht nur an api.github.com und wird nicht auf die Festplatte geschrieben. In der Praxis braucht die Kommandozeile ein eigenes GitHub-Token mit Lesezugriff auf öffentliche Repositories, weil GitHub anonyme Anfragen stark begrenzt.

Dasselbe Repository ergibt dieselben Bytes im Bericht, egal was vorher lief. Feste Referenzberichte im Repository halten das fest, Byte für Byte. Ein Urteil, das von Zufall oder Reihenfolge abhinge, ließe sich weder prüfen noch vergleichen.

{{I:shield-check}} Was RepoCanary ist und was nicht

Ein Rauchmelder, kein Schutzschild. Es erkennt die bekannte Form eines Angriffs in Dateien. Ein Repository, das seine Nutzlast erst zur Laufzeit von einem Server holt, kann grün durchgehen. Deshalb heißt Grün nie „sicher“ (Kapitel 12).

04

Wie ein Scan läuft

Ein Scan hat sieben Schritte. Die ersten vier entscheiden, was gelesen wird, die letzten drei, was es bedeutet.

{{FIG:pipeline|Abb. 3|Sieben Schritte. Der Baum wird gelesen und nach Orten sortiert, an denen eine Falle liegen muss. Was eine Datei ausführen lässt, wird gezielt nachgeholt. Dann läuft jede Regel auf jeder Datei, die Schwere ergibt die Farbe, und der Bericht nennt zu jedem Befund Datei, Zeile, Grund und nächsten Schritt.}}

Auswählen und nachverfolgen

Ein Repository kann groß sein, der Scan liest nicht alles. Deshalb kommt zuerst, was laufen muss, bevor jemand liest: Install-Hooks, Autostarts von Editor und Agenten, Lockfiles, Build-Skripte. Jede dieser Arten hat ein eigenes Kontingent, damit keine das ganze Budget aufbraucht. Gewöhnlicher Quellcode füllt den Rest.

Ein postinstall, das node scripts/setup.js startet, eine Kette von npm run, ein bin-Eintrag, ein VS-Code-Task: Was eine Datei ausführen lässt, wird mit einem eigenen, reservierten Budget nachgeholt. So kann ein großes Repository die eine Datei nicht verdrängen, an der das Urteil hängt. Wird eine Obergrenze erreicht, sagt der Bericht das als Hinweis.

Der Bericht

Jeder Befund nennt Datei und Zeile, erklärt in einfachen Worten, warum er zählt, und sagt, was als Nächstes zu tun ist. Ausschnitte werden vor der Ausgabe gekürzt, lange kodierte Folgen geschwärzt, damit keine funktionierende Nutzlast im Bericht landet.

05

Was es erkennt

Der Katalog umfasst über 100 Techniken aus den Kampagnen und dem breiteren Werkzeugkasten von Angriffen über npm und PyPI, in neun Kategorien. Er ist gemessen, nicht behauptet.

{{PHONE:coverage}}

Jede Technik liegt als ganzes, glaubwürdiges Repository mit wirkungslosen Endpunkten bei. Ein Skript lässt die echte Engine über alle Beispiele laufen und schreibt auf, welche Regeln feuern und welches Urteil herauskommt. Daraus entstehen der Katalog im Repository und die Seite /coverage der Website. Die Prüfstrecke scheitert, wenn Katalog und Regeln auseinanderlaufen oder wenn eine Technik nicht mehr erkannt wird.

Vorbild sind die öffentlich beschriebenen Familien Contagious Interview, BeaverTail, InvisibleFerret und OtterCookie. Etwa zwei Drittel der Techniken ergeben Rot, der Rest Gelb, keine bleibt grün.

Dateien, die einem KI-Agenten Anweisungen geben, sind ein eigener Fall. RepoCanary erkennt die mechanischen Tricks darin, etwa versteckten Text, unsichtbare Tag-Zeichen oder einen Link, der ein Geheimnis mitnimmt. Eine Bitte in gewöhnlicher Sprache, die einen Agenten zu etwas Schädlichem bringen soll, kann es nicht beurteilen.

Eine VS-Code-Aufgabe, die beim Öffnen des Ordners startet, ist immer Rot, egal was sie startet: In einem fremden Repository ist schon das Öffnen zum Lesen der Angriff.

{{FIG:categories|Abb. 5|Neun Kategorien, jede mit Beispielen. Kontextsignale wie ein brandneues Konto stehen gestrichelt: Sie können allein höchstens zu Gelb führen, nie zu Rot.}}

Der Katalog ist eine Absicherung gegen Rückschritte, keine Erkennungsrate. Jede Regel braucht ein Beispiel, also deckt der Katalog per Bauart nur ab, was die Regeln ohnehin fangen. Eine ehrliche Erkennungsrate bräuchte Schadcode, den jemand anderes geschrieben hat, geprüft mit eingefrorenen Regeln. Die gibt es noch nicht, und das Repository sagt es selbst.

06

Das Urteil

Die statischen Regeln entscheiden das Urteil, und nichts sonst. Die Regeln dafür sind so einfach, dass jede in einen Satz passt.

{{FIG:verdict|Abb. 6|Wie die Farbe entsteht, mit dem Exit-Code der Kommandozeile. Ein Scan, der nicht fertig wurde, endet mit Code 3, nie mit Grün.}}

Schwache Signale, die dieselbe Beobachtung beschreiben, zählen als eine: Eine minifizierte Bibliothek löst mehrere Regeln zu kodiertem Inhalt aus, ist aber nur eine Tatsache über das Projekt.

Die KI-Zweitmeinung

Mit --ai gehen die Befunde an ein Sprachmodell, mit dem eigenen Schlüssel der Nutzer: Pfade, geschwärzte Ausschnitte, Gründe und öffentliche Daten des Repositorys, nichts vom eigenen Rechner. Vier Anbieter sind möglich, zwei mit kostenlosem Zugang. Ein Schlüssel wird nie als Argument angenommen und bleibt nur für den Lauf im Speicher.

{{FIG:ai|Abb. 7|Was die KI darf: ein Grün zu Gelb anheben und ein Gelb freigeben, wenn jedes Signal eindeutig harmlos ist. Ein Rot senken oder erzeugen darf sie nie.}}
07

Drei Oberflächen, eine Engine

Kommandozeile, Website und GitHub Action führen denselben Detektor aus. Eine Regel verhält sich deshalb überall gleich.

{{FIG:surfaces|Abb. 8|Eine Engine in reinem Node, ohne Laufzeit-Abhängigkeiten, dahinter vier Wege zum Urteil. Die Exit-Codes sind in Kommandozeile und Action dieselben, und Code 3 ist nie ein Erfolg.}} {{PHONE:home}}

Kommandozeile. npx repocanary owner/repo braucht keine Installation und kein Konto, nur Node. Die Ausgabe gibt es als Text, als versioniertes JSON und als SARIF für GitHub Code Scanning.

Website. Wer kein Terminal nutzt, fügt auf repocanary.com den Link ein und liest dasselbe Ergebnis. Auch dort wird nichts aus dem Repository ausgeführt oder auf dem eigenen Rechner gespeichert. Die Seite braucht kein Konto, setzt keine Cookies und misst keine Besucher.

GitHub Action. Ein Workflow kann ein Repository prüfen, bevor jemand im Team es ausführt, und den Schritt ab einem Urteil scheitern lassen. Das README rät, die Action über den vollen Commit-Hash einzubinden, nicht über ein Tag: Ein Tag lässt sich verschieben, und die Action läuft mit dem Token des eigenen Runners.

Badge. Ein Projekt kann neben dem CI-Status zeigen, was RepoCanary über es sagt. Konnte der Scan nicht laufen, steht „unavailable“ da, nie ein grünes Abzeichen.

Wer die Website selbst betreiben will, braucht weder Datenbank noch Warteschlange, nur ein GitHub-Token.

09

Gemessen

Ein Scanner sieht auf dem Code gut aus, auf den er abgestimmt wurde. Gezählt hat deshalb die Messung auf Repositories, die vorher niemand geprüft hatte. Die Zahlen in diesem Kapitel stammen aus der Messung des Projekts bis zum 24. September 2026.

4.002 nie gesehene Repositories wurden in 29 Wellen geprüft. Jedes Rot einer Welle wurde geöffnet und gelesen, und die Regeln wurden für die Fehler korrigiert, bevor die nächste Welle gezogen wurde. Ab Welle 16 wurde der Pool absichtlich schwerer: bekannte Projekte, Krypto- und Handelsbots, Werkzeuge für Coding-Agenten und die neuesten Repositories der großen Sprachen, die beruflich Dienste installieren und Installer in eine Shell leiten. Zugleich wurden die Regeln vor jeder Ziehung eingefroren.

{{FIG:wrongreds|Abb. 9|Falsche Rote je Welle, in Prozent der Repositories. Auf breiten Ziehungen fiel der Anteil von 13 Prozent auf unter 1 Prozent bei 246 Probeaufgaben. Auf dem schwereren Pool mit eingefrorenen Regeln fiel er von 9 Prozent auf 2,75 Prozent (33 von 1.198 in den Wellen 24 bis 29). Werte aus der Projektdokumentation.}}

Auf dem schweren Pool trifft Rot also etwa jedes 36. ehrliche Repository. Das ist die ehrliche Grenze eines Scanners, der Dateien liest und nichts ausführt. Viele dieser Rote sind nicht einmal falsch im engeren Sinn: Ehrliche Projekte tun manchmal genau, was der Angriff tut, etwa einen Installer aus einem Wurzel-Skript in eine Shell leiten oder einen Dienst einrichten, der beim Anmelden startet. Der Bericht sagt, was der Code tut. Ob das gewollt ist, entscheiden die Lesenden.

Sicherheit und Datenschutz

Ein Scanner für feindliche Eingaben muss selbst feindlichen Eingaben standhalten. Und eine Sicherheitsaussage ist nur so viel wert wie das, was verhindert, dass sie sich still ändert.

BereichUmsetzung heute
AusführungKein Klonen, kein Installieren, kein eval, kein child_process. Ein Test im Build hält das fest.
NetzNur api.github.com und, auf Wunsch, der gewählte KI-Anbieter. Auch das prüft ein Test.
AufwandJede Regel mit linearem Aufwand, gemessen an Dateien, die zum Verlangsamen gebaut sind. Der schlimmste gemessene Fall lag bei 2,4 Sekunden.
AusgabeSteuer- und Richtungszeichen werden entschärft, damit kein Repository die Anzeige im Terminal fälschen kann. Lange kodierte Folgen werden geschwärzt.
SchlüsselNie als Argument, eingefügt unsichtbar, nur für einen Lauf im Speicher, nie auf der Festplatte und nie im Bericht.
WebsiteKein Konto, keine Cookies, keine Analyse, nichts auf der Festplatte. Der geprüfte Link geht nur an GitHub.
LieferketteKeine Laufzeit-Abhängigkeiten. Abhängigkeiten der Website werden bei jedem Push auf bekannte hohe Lücken geprüft. Actions sind auf Commit-Hashes festgelegt.
VeröffentlichenNur von einem Tag auf der Hauptlinie, nach derselben Prüfstrecke wie die CI, mit Freigabe durch eine Person und Herkunftsnachweis. Ein Token zum Veröffentlichen existiert nicht.
MeldestelleSicherheitslücken vertraulich über den Security-Tab des Repositorys, Erkennungslücken als gewöhnliches Issue mit dem Link.

Die Website hängt an einer Webanwendung mit eigenen Abhängigkeiten. Als im November 2026 kritische Sicherheitshinweise für das Framework der Website erschienen, wurde es aktualisiert.   • Offline-Tests. Über 750 Tests in über 20 Dateien laufen in rund 25 Sekunden ohne Netz und ohne Installation. Die Zeilenabdeckung des Engine-Codes liegt über 95 Prozent.

Grenzen heute

Ein Manifest, das seine Grenzen verschweigt, verdient kein Vertrauen. RepoCanary ist ein Rauchmelder, kein Schutzschild.

Nur Bekanntes in Dateien

Nutzlast, die erst zur Laufzeit von einem Server kommt, eine kompromittierte Abhängigkeit, die normal aus der Registry kommt, und neue Techniken ohne Regel können grün durchgehen.

Angriffe ohne Code

Anweisungen per Chat, die Bitte, einen fremden CI-Runner einzurichten, oder eine Bitte an einen KI-Agenten in gewöhnlicher Sprache liegen außerhalb dessen, was ein Dateiscan sehen kann.

Nicht alles wird gelesen

Binärdateien, Submodule und Ziele symbolischer Links liest RepoCanary nicht, und große Repositories nur zum Teil. Jeder solche Fall steht als Hinweis im Bericht.

Rot trifft auch Ehrliche

Gemessen trifft Rot etwa jedes 36. ehrliche Repository im schweren Pool. Wer Rot sieht, liest den Befund, bevor er urteilt.

Keine echte Erkennungsrate

Der Katalog ist eine Absicherung gegen Rückschritte. Eine Messung an Schadcode von Dritten mit eingefrorenen Regeln steht aus.

Kein externes Audit

Die Website ist nicht Zeile für Zeile geprüft, der GitHub-Client nicht mit feindlichen API-Antworten gefuzzt, die KI-Zweitmeinung nicht gegen Text getestet, der das Modell manipulieren soll. Eine Person baut und betreut das Projekt.

Was nicht geprüft ist

„Nicht geprüft“ ist ein gültiger Stand. Diese Punkte stehen in den Quellen, wurden für dieses Manifest aber nicht gegen die Wirklichkeit nachgeprüft:

  • Die Zahlen aus Kapitel 9 (Wellen, falsche Rote, Korpus, 71 Projekte, 19 Fallen, schlimmster Fall von 2,4 Sekunden) stammen aus der Messung des Projekts bis September 2026. Wiederholt wurde sie für dieses Manifest nicht. Die Fallen wurden nicht einzeln nachgeprüft.
  • Die zwei Rückschritte, die der wöchentliche Korpuslauf fand, sind nur in der Beschreibung des Workflows belegt.
  • Die Zahl der Commits und Pull Requests im privaten Entwicklungs-Repository lässt sich öffentlich nicht nachprüfen.
  • Nachgeprüft sind die 750+ Offline-Tests, die 40+ Tests der Website, die Abdeckung und der aktuelle Katalog: Sie liefen für dieses Manifest grün. Das rote Ergebnis auf den Bildschirmfotos ist die Offline-Prüfung des Beispiels im Repository, eingespielt in die echte Website. Startseite, grünes Beispiel und Katalog sind live.
  • Wie die Website im Betrieb verfügbar war, ist nicht gemessen.
