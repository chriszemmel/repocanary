Manifesto

Read, never run. Judge honestly. Publish the limits.

RepoCanary checks a GitHub repository for the known signatures of fake-job-interview malware without ever running a line of it. This manifesto says what the project believes, how it is built, what it does today and where it stops.

01

What we believe

Someone asked to run a stranger’s repository usually has a few minutes and no tool for the job. RepoCanary gives that person a fast, free and honest read. The project follows seven principles. Each is built into the code, and each has a real case behind it.

Sept. 27, 2026first release on npm and public on GitHub
100+documented attack techniques, each caught in the catalog
90+detection rules the catalog fires
750+automated tests, offline, nothing to install
4,000+repositories measured that the rules had never seen
0runtime dependencies, and 0 lines of the target ever run
1

Read, never run

RepoCanary never clones, installs, executes, evaluates or imports the repository it checks. It reads files as text and matches patterns.

Why

A tool that ran a stranger’s code to check it would be the attack. Pointing RepoCanary at malware must risk no more than reading the files in a browser.

The case

A test fails the build as soon as the engine imports child_process, uses eval, or contacts any host other than the GitHub API and, only when asked, an AI provider (test/invariants.test.js). When the docs promised the code was “never downloaded”, they were corrected: files are read into memory to be checked, but never run or saved.

2

Green does not mean safe

A green verdict says “nothing known matched” and never more. A scan that could not finish never passes itself off as one that found nothing.

Why

False reassurance is the most expensive result a tool like this can give. People who read “safe” run the code. A check that could not look must not look like one that found nothing.

The case

The sentence for green lives in one place in the code and is used verbatim everywhere. A test checks that it says outright: not proof of safety. An incomplete scan ends with exit code 3, still writes a JSON or SARIF document with the verdict “error”, and fails the GitHub Action under every setting.

3

Red has to be worth believing

Red is kept for the shape of a trap. Anything uncertain is yellow. How often red hits an honest project is measured on code nobody tuned for, not estimated.

Why

A warning that fires on honest projects teaches people to skip it. Then the real red is worthless too.

The case

In the first measurement wave, about 13 percent of red verdicts were wrong. Each mistake was fixed with a general principle, never an exception: red needs something that runs by itself. Text is not a command until it reaches a shell. Mentioning is not doing (chapter 9).

4

The limits live in the repository

What RepoCanary does not catch is written into its threat model. The most important limits ship as samples that must keep getting through.

Why

A security tool that hides its limits misleads exactly the people who most need the truth.

The case

Six documented limits are kept as runnable samples, and the benchmark asserts they are still missed, so a limit that quietly moves gets noticed. RepoCanary reports its own repository as red, because it has to contain its signatures. An exemption would be an evasion path, so there is none.

5

A model never decides red

An AI second opinion is available, but only on request and with the user’s own key. It may clear a yellow or raise a green. It may never lower a red or produce one.

Why

Red means a signature fired. A model’s opinion is not a signature. And models often decline questions about malware, so the verdict cannot depend on one answering.

The case

The bound sits in the code that merges the verdict, not in the prompt, and tests hold it in place. If a provider declines or fails, the next one is tried, then the static verdict stands. When the AI was told the length of the capped findings list instead of the true count, that was fixed.

6

Hostile input is the normal case

What RepoCanary reads was often written by an attacker. Every rule has to survive crafted files without hanging, crashing or letting the output be forged.

Why

A scanner that one crafted file can stall, or trick into an empty report, delivers nothing exactly when it matters.

The case

Every rule is held to linear cost, measured on hostile files at the largest size a scan accepts. If a rule still fails, it costs only that file’s findings. Control and bidirectional characters are neutralized before output, so no repository can spoof the terminal.

7

Open and free

The code and the rules are public under the MIT license. There is no account, no telemetry and no paid tier.

Why

The person RepoCanary is for cannot buy a scanner. And nobody should trust a security tool nobody can audit.

The case

The CLI has no runtime dependencies, and a lint step enforces that. The npm package is published through Trusted Publishing with provenance. No publishing token exists anywhere.

{{I:triangle-alert}} Red

A high-severity signature matched. Do not run it, do not install it, do not open it in an editor that runs tasks by itself.

{{I:eye}} Yellow

Something looks suspicious but has an honest explanation in some projects. Have someone read the flagged lines first.

{{I:circle-check}} Green

Nothing known matched. That lowers the risk but proves nothing, and the report says so.

02

The problem

Someone sends a repository and asks you to run it, or just open it: a recruiter with a take-home task, a “client”, someone who wants a second opinion. The payload sits where it runs before you have read anything.

{{FIG:attack|Fig. 1|The attack. A repository arrives with a request to run it. Through the install, by opening the folder, or on first start: the payload runs before anyone has read the code, and takes what is on the machine.}}

Campaigns like “Contagious Interview”, attributed to North Korean state actors, have used this against thousands of developers, and ordinary criminals now copy the tooling. A postinstall script, an obfuscated config file, a poisoned lockfile entry, or no install step at all: a VS Code task that runs when the folder opens, an MCP server an AI editor starts by itself, an agent hook or a dev container.

{{I:hourglass}} Runs before reading

The trap sits in install hooks and autoruns. Reading first only helps if you know where to look.

{{I:folder-open}} Opening is enough

Some paths need no command at all. Opening the folder in an editor to look at it is already the attack.

{{I:file-search}} Code as bait

The visible code is often harmless. It only fetches what arrives at run time.

03

The idea

RepoCanary checks before the code reaches your editor or terminal, and it only reads. Pointing it at malware carries no more risk than reading the files in a browser.

{{FIG:safe|Fig. 2|Read, never run. RepoCanary fetches the file tree and selected files as plain text through the GitHub API. Findings go to an AI provider only on request. Cloning, installing, executing, evaluating and importing do not exist in the code, and a test fails the build if that changes.}}

RepoCanary reads a bounded selection of files from the repository. Every check is plain text and pattern matching. The scanned link goes to api.github.com and nowhere else, and it is never written to disk. In practice the CLI needs a GitHub token with read access to public repositories, because GitHub limits anonymous requests tightly.

The same repository produces the same bytes in the report, whatever ran before. Reference reports in the repository pin that down, byte for byte. A verdict that depended on chance or ordering could be neither checked nor compared.

{{I:shield-check}} What RepoCanary is, and is not

A smoke detector, not a force field. It recognizes the known shape of an attack in files. A repository that fetches its payload from a server at run time can pass as green. That is why green never means “safe” (chapter 12).

04

How a scan runs

A scan has seven steps. The first four decide what gets read, the last three what it means.

{{FIG:pipeline|Fig. 3|Seven steps. The tree is read and ranked by where a trap has to live. Whatever a file says will run is fetched on purpose. Then every rule runs on every file, severity sets the color, and the report gives each finding its file, line, reason and next step.}}

Select and follow

A repository can be large, and a scan does not read everything. So what has to run before anyone reads comes first: install hooks, editor and agent autoruns, lockfiles, build scripts. Each kind has its own quota, so none can spend the whole budget. Ordinary source fills the rest.

A postinstall that runs node scripts/setup.js, an npm run chain, a bin entry, a VS Code task: whatever a file says will execute is fetched on a reserved budget of its own. A large repository cannot crowd out the one file the verdict depends on. When a cap is reached, the report says so in a note.

The report

Every finding names the file and line, explains in plain language why it matters, and says what to do next. Snippets are shortened before output and long encoded runs are redacted, so no working payload ends up in the report.

05

What it detects

The catalog covers more than 100 techniques from the campaigns and the wider npm and PyPI attack playbook, in nine categories. It is measured, not asserted.

{{PHONE:coverage}}

Each technique is reproduced as a whole, plausible repository with inert endpoints. A script runs the real engine over every sample and records which rules fire and what verdict results. That output becomes the catalog in the repository and the website’s /coverage page. The gates fail if the catalog drifts from the rules or a technique stops being caught.

The models are the publicly documented families Contagious Interview, BeaverTail, InvisibleFerret and OtterCookie. About two thirds of the techniques get red, the rest yellow, and none stays green.

Files that give instructions to an AI agent are a case of their own. RepoCanary catches the mechanical tricks in them, such as hidden text, invisible tag characters or a link that carries a secret out. It cannot judge a plain-language request meant to talk an agent into something harmful.

A VS Code task that runs when the folder opens is always red, whatever it runs: in a stranger’s repository, opening it to read it is already the attack.

{{FIG:categories|Fig. 5|Nine categories, each with examples. Context signals such as a brand-new account are dashed: on their own they can lead to yellow at most, never to red.}}

The catalog is a regression guard, not a detection rate. Every rule needs a sample, so by construction the catalog only covers what the rules already catch. An honest detection rate needs malware written by someone else, scanned on frozen rules. There is none yet, and the repository says so itself.

06

The verdict

The static rules decide the verdict, and nothing else does. The rules for it are simple enough that each fits in one sentence.

{{FIG:verdict|Fig. 6|How the color is decided, with the CLI’s exit code. A scan that could not finish ends with code 3, never with green.}}

Weak signals that describe the same observation count as one: a minified library trips several encoded-content rules at once, but it is a single fact about the project.

The AI second opinion

With --ai, the findings go to a language model on the user’s own key: paths, redacted snippets, reasons and public repository metadata, nothing from the user’s machine. Four providers are supported, two with a free tier. A key is never accepted as an argument and is held in memory for that run only.

{{FIG:ai|Fig. 7|What the AI may do: raise a green to yellow, and clear a yellow when every signal is clearly benign. It may never lower a red or produce one.}}
07

Three surfaces, one engine

The CLI, the website and the GitHub Action run the same detector. A rule behaves the same everywhere.

{{FIG:surfaces|Fig. 8|One engine in plain Node with zero runtime dependencies, and four ways to a verdict behind it. The exit codes are the same in the CLI and the Action, and code 3 is never a success.}} {{PHONE:home}}

CLI. npx repocanary owner/repo needs no install and no account, only Node. Output comes as text, as versioned JSON, and as SARIF for GitHub code scanning.

Website. Anyone without a terminal pastes the link on repocanary.com and reads the same result. Nothing from the repository is run there or saved on the visitor’s machine. The site needs no account, sets no cookies and runs no analytics.

GitHub Action. A workflow can scan a repository before anyone on the team runs it, and fail the step at a chosen verdict. The README advises pinning the Action by full commit SHA rather than by tag: a tag can be moved, and the Action runs with the token of your own runner.

Badge. A project can show what RepoCanary says about it next to its CI status. If the scan could not run, the badge reads “unavailable”, never green.

Hosting the website yourself needs no database and no queue, only a GitHub token.

09

Measured

A scanner always looks good on the code it was tuned on. So the measurement that counted was on repositories nobody had scanned before. The numbers in this chapter come from the project’s measurement up to September 24, 2026.

4,002 unseen repositories were scanned in 29 waves. Every red in a wave was opened and read, and the rules were fixed for what the wave got wrong before the next one was drawn. From wave 16 the pool got harder on purpose: famous projects, crypto and trading bots, coding-agent tooling, and the newest repositories in the big languages, which install services and pipe installers into shells for a living. At the same time, the rules were frozen before each draw.

{{FIG:wrongreds|Fig. 9|Wrong reds per wave, as a percentage of repositories. On broad draws the rate fell from 13 percent to under 1 percent on 246 take-home tasks. On the harder pool with frozen rules it fell from 9 percent to 2.75 percent (33 of 1,198 in waves 24 to 29). Values from the project documentation.}}

On the hard pool, then, red hits about one honest repository in 36. That is the honest limit of a scanner that reads files and runs nothing. Many of those reds are not even wrong in the narrow sense: honest projects sometimes do exactly what the attack does, such as piping an installer into a shell from a root script, or writing a service that starts at login. The report says what the code does. Whether that is wanted is the reader’s call.

Real traps found while measuring

Measurement up to September 24, 2026

While measuring, RepoCanary found 19 live traps in the wild, 13 of them from a single account. Among them: an obfuscated loader hidden far to the right of the visible part of a line that npm start runs, a trading bot built with an obfuscator, and a script that executes whatever a URL returns. This manifesto names neither accounts nor repositories.

2

Well-known, difficult projects

Measurement up to September 24, 2026

On 71 well-known projects chosen because they are hard (native addons, package managers, crypto libraries, build systems), 53 were green and two were red, both correctly: one installs a boot service, the other pipes an installer into a shell in its dev container.

Security and privacy

A scanner for hostile input has to withstand hostile input itself. And a security guarantee is only worth what stops it from quietly changing.

AreaHow it works today
ExecutionNo cloning, no installing, no eval, no child_process. A test in the build holds this in place.
NetworkOnly api.github.com and, on request, the chosen AI provider. A test checks this too.
CostEvery rule at linear cost, measured on files built to be slow. The worst case measured was 2.4 seconds.
OutputControl and bidirectional characters are neutralized, so no repository can forge what the terminal shows. Long encoded runs are redacted.
KeysNever as an argument, hidden when pasted, held in memory for one run, never on disk and never in a report.
WebsiteNo account, no cookies, no analytics, nothing written to disk. The scanned link goes to GitHub only.
Supply chainNo runtime dependencies. The website’s dependencies are checked for known high advisories on every push. Actions are pinned to commit SHAs.
PublishingOnly from a tag on the main branch, after the same gates as CI, with a human approval step and provenance. No publishing token exists.
ReportingVulnerabilities privately through the repository’s Security tab, detection gaps as an ordinary issue with the link.

The website rests on a web framework with its own dependencies. When critical security advisories for that framework appeared in November 2026, it was upgraded. The CLI was not affected: it has no dependencies. There is no third-party review (chapter 12).

The gates

{{FIG:gates|Fig. 11|Every push and every pull request runs the same steps. Each week the guard with every confirmed red and the whole corpus are added. Publishing only happens after the same gates, from a tag on the main branch, with a human approval step.}}
  • Offline tests. More than 750 tests in more than 20 files run in about 25 seconds with no network and nothing to install. Line coverage of the engine code is above 95 percent.
  • Reference reports. Text, JSON and SARIF output are compared byte for byte against fixed reports.
  • The guard. Most fixes narrow a rule so a wrong red stops firing, and every one of those can only cost detection. So the guard checks every sample, every documented evasion and every confirmed red: nothing caught once may slip through.
  • Website. More than 40 tests of its own, type checking and a build in a separate job, because the site imports the engine directly.

12

Limits today

A manifesto that hides its limits does not deserve trust. RepoCanary is a smoke detector, not a force field.

Only what is known, in files

A payload fetched from a server only at run time, a compromised dependency that resolves normally from the registry, and new techniques with no rule yet can all pass as green.

Attacks without code

Instructions sent over chat, a request to register someone’s CI runner, or a plain-language request to an AI agent are outside what a file scan can see.

Not everything is read

RepoCanary does not read binary files, submodules or symlink targets, and reads large repositories only in part. Each such case appears as a note in the report.

Red hits honest projects too

As measured, red hits about one honest repository in 36 on the hard pool. Read the finding before you judge the project.

No real detection rate

The catalog is a regression guard. A measurement on malware written by others, on frozen rules, is still to come.

No external audit

The website has not been reviewed line by line, the GitHub client has not been fuzzed against hostile API responses, and the AI pass has not been tested against text written to manipulate the model. One person builds and maintains the project.

What is not verified

“Not verified” is a valid status. These points are in the sources, but were not checked against reality for this manifesto:

  • The numbers in chapter 9 (waves, wrong reds, corpus, 71 projects, 19 traps, the 2.4-second worst case) come from the project’s measurement up to September 2026. It was not repeated for this manifesto, and the traps were not rechecked one by one.
  • The two regressions the weekly corpus run found are documented only in the workflow’s description.
  • The commit and pull request counts of the private development repository cannot be checked publicly.
  • Verified: the 750+ offline tests, the 40+ website tests, the coverage and the up-to-date catalog all passed for this manifesto. The red result in the screenshots is the offline scan of the repository’s example, played into the real website. The home page, the green example and the catalog are live.
  • The website’s availability in operation has not been measured.
